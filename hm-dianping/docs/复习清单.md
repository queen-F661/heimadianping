- [x] Redisson（10/24，10/30 已过）  
  过关：能说清看门狗续期机制、可重入怎么实现、和手写 setnx 的区别
  > **源码要点**（`org/redisson/RedissonLock.java`，3.13.6）
  >
  > - **加锁三分支**：锁不存在 → `hincrby` 创建（count=1）；`hexists` 是我 → `hincrby` 重入（count+1）；都不是 → 返回 `pttl`（失败，附带对方剩余时间）
  > - **返回值语义**：`nil` = 加锁成功，`pttl` 数字 = 失败。Java 侧靠 `ttlRemaining` 判断要不要启动看门狗
  > - **field 是 `RedissonClient的uuid:threadId`**，所以只有"同一个线程"才认得出，这是可重入的前提
  > - **没有看门狗的条件**：`tryAcquireOnceAsync` 开头 `if (leaseTime != -1) return ...`，一旦手动指定租期就直接返回
  > - **看门狗本体是 `renewExpiration()`**：延迟 `internalLockLeaseTime / 3`（10 秒）执行 → `hexists` 确认锁还是自己的才 `pexpire` → 返回 1 就在回调里再调一次自己（自循环），返回 0 链条自动断
  > - **停止的三道保险**：`unlock` → `cancelExpirationRenewal` 取消任务；任务执行时 Map 里查不到就直接 return；`hexists` 返回 0 不再续
  > - **重入场景不会提前停**：只有 `hasNoThreads()` 为真（最后一个持有者释放）才真正 `timeout.cancel()`
  > - 定时器用的是 Netty 的 `HashedWheelTimer`（时间轮），不是 `ScheduledExecutorService`
  > - 进程崩溃时定时任务随进程死，锁 30 秒自然过期——这就是"兜底"
- [x] 阻塞队列异步下单（10/25）  
  过关：能说清为什么要把下单和库存扣减拆开、内存阻塞队列的两个致命问题（重启丢单、内存溢出）
- [x] Stream 消息队列（10/27）  
  过关：能说清消费者组、ACK、pending list 的作用，以及为什么比内存队列可靠

  > **四个概念，用"我 vs 我们"记**
  > - **消费者 c1** = 一个干活的人（线程挂的工牌），对应 `CONSUMER_NAME`
  > - **消费者组 g1** = 一群人，记着"我们整体读到哪了"（last-delivered-id），保证一条消息只给组里一个人
  > - **pending list** = 每个人的欠账本，挂在组下面，记"谁领了还没 ACK"；存的是消息 ID，不是消息副本
  > - **ACK** = 核销，处理完从 pending 里划掉
  >
  > **组内分活（不重复），组间各拿一份（广播）**
  >
  > **至少一次语义**：先记账再干活，崩了能重做 → 所以业务必须幂等（`createVoucherOrder` 里查数据库兜底就是干这个）
  >
  > **排查命令**：`XINFO GROUPS stream.orders`、`XPENDING stream.orders g1`
  >
  > **两个坑**：① `CONSUMER_NAME` 要固定，重启后才捞得回自己的 pending；② 多实例部署时每台必须不同，否则账混在一起

**演进题（必答）**：一人一单从 JVM 锁到 Redisson 一共跳了几次？每次是因为发现了什么问题才跳的？这条线讲不顺，等于没学。

| 跳 | 从 → 到 | 触发问题（上一步哪里撑不住了） |
|---|---|---|
| **1** | `synchronized` → Redis 分布式锁 | 部署两台机器，两个 JVM 各一把锁，**锁不互通**（不是"单线程"，是单进程） |
| **2** | 裸 `setnx` → uuid + Lua | 锁 10 秒到期自动释放，A 恢复后执行 finally，**删了 B 的锁** |
| **3** | 手写锁 → Redisson | 不可重入、不可重试（while 空转）、业务超时锁就没了、释放还得自己写 Lua |
| **4** | 加锁 → **Lua 原子扣减** | 全员排队，1000 人占满 Tomcat 线程，第 1001 人连排队资格都没有 |
| **5** | 同步 → **异步队列** | Lua 之后还要落库，这一步还是同步的，用户还得等 |
| **6** | 内存队列 → **Stream** | 重启丢单、内存溢出、多实例不共享 |

**记法：别背步骤，背痛点。** 每次问一句"上一版到底哪里疼"——每一跳都是被逼出来的，没有一步是为了显得高级。

**三层安全由谁保证**（秒杀线最短的一张表）

| 阶段         | 在哪做            | 并发靠什么挡住     | 需要锁吗          |
| ---------- | -------------- | ----------- | ------------- |
| ① 同步下单     | Java + MySQL   | 什么都挡不住      | 不需要（会超卖）      |
| ② 加锁串行化    | Java + Redis 锁 | 锁把四步围成整体    | **需要**        |
| ③ Lua 预扣库存 | Redis          | Lua 把四步压成一步 | **不需要**       |
| ③' 异步落库    | Java + MySQL   | Redisson 锁  | **需要**（防重复消费） |

一句话：**锁是胶水，把多步粘成一个整体；Lua 是模具，直接一次成型。能一次写完的地方，就不需要锁。**

易混点："一人一单"在 Redis 里靠 Lua 保证，在 MySQL 里靠 Redisson 锁保证。不是因为哪个高级，而是看在目标系统里能不能一次做完。
