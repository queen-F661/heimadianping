## 秒杀下单报错诊断：Unknown column 'voucherId'

- 现象：`BadSqlGrammarException` → `MySQLSyntaxErrorException: Unknown column 'voucherId' in 'where clause'`，
  生成的 SQL 为 `UPDATE tb_seckill_voucher SET stock = stock -1 WHERE (voucherId = ?)`。
- 根因：`VoucherOrderServiceImpl#seckillVoucher` 第 260 行写成 `.eq("voucherId", voucherId)`。
  MyBatis-Plus 的**字符串重载** `eq(String column, Object val)` 里的 column 是**数据库列名**，
  不做驼峰转下划线，直接拼进 SQL；而 `tb_seckill_voucher` 的真实列名是 `voucher_id`（实体里 `@TableId(value = "voucher_id")`）。
  同文件第 225 行写的 `.eq("voucher_id", voucherId)` 才是对的 —— 这是最直观的对照。
- 顺带指出的问题（未改代码，用户自己动手）：
  1. 第 260 行 update 缺 `.gt("stock", 0)`，查库存与扣库存是两步、非原子，有超卖风险。
  2. 第 252-253 行 `!isBefore(endTime)` 分支返回文案写成了"当前时间未开始活动"，应为"活动已结束"。
  3. `seckillVoucherService.getById(voucherId)` 未判空，券不存在时 NPE。
  4. `seckillVoucher(Long)` 这个同步版本（243-274 行）与项目已搭好的 `seckill.lua + Stream 异步下单 + Redisson 一人一单`
     架构不一致，像是旧版本残留。
- 结论：列名不要凭 Entity 字段名猜，MP 字符串方式写的是 DB 列名；能写 Lambda 就写 Lambda，编译期就能挡掉这类错。
- 用户已自行把第 260 行改成 `.eq("voucher_id", voucherId)`。

## 追加发现：seckillVoucher() 订单根本没落库（丢单 bug）

- `seckillVoucher(Long)`（243-274 行）里 `new VoucherOrder()` 只设置了 id / userId / voucherId 三个字段，
  **从没调用 `save()`**，第 273 行直接 `return Result.ok(orderId)` → 对象造完就丢，`tb_voucher_order` 一行都不会插。
- 而第 260 行已经先把 `tb_seckill_voucher.stock` 扣了 1 → 结果最坑：**库存扣了、订单没记录**。
- 对照：同文件第 234 行 `save(voucherOrder)` 才是真正往 `tb_voucher_order` 插入的动作（在 `createVoucherOrder` 里）。
- 两张表职责区分（DB 事实，来自 db/hmdp.sql）：
  - `tb_seckill_voucher`：主键 `voucher_id`，字段 stock / create_time / begin_time / end_time / update_time。**改库存**。
  - `tb_voucher_order`：主键 `id`(IdType.INPUT，故必须自己 setId)，user_id / voucher_id / pay_type(默认1) / status(默认1) /
    create_time(默认 CURRENT_TIMESTAMP) / update_time。**存订单**。
  - pay_type 与 status 有 DB 默认值、create_time 有 DEFAULT CURRENT_TIMESTAMP，所以只 set 三个字段也能插入成功。
- 前置提醒：`setSql("stock = stock -1")` 和 `.eq("voucher_id", ...)` 里写的都是**数据库列名**，这点是对的；
  别把 setSql 的列名和 eq 的列名混成 Java 字段名。

## 一条被误当报错的日志：MySQL 驱动的 SSL 噪音（无害）

- 用户贴来的大段日志里**没有一条真正的业务 ERROR**，全是两类 `WARN`：
  1. `WARN: Establishing SSL connection without server's identity verification is not recommended...`
  2. `WARN: Caught while disconnecting... javax.net.ssl.SSLException: closing inbound before receiving peer's close_notify`
- 根因同一个：`application.yaml` 的 JDBC url 没显式关 SSL，mysql-connector-java 5.1.47 在建连 / 回收连接时就唠叨。
  它甚至会在 `** BEGIN NESTED EXCEPTION **` 这种吓人的格式里打印，但只是 WARN，不影响功能。
- 消掉办法：url 后面加 `&useSSL=false`（当前 url 已有 `allowPublicKeyRetrieval=true`，就缺这一项）。
  彻底点可以升级到 mysql-connector-java 8.0.x。
- 日志里两种时间格式的来源：`logging.pattern.dateformat: mm:ss.SSS` 只管应用日志（所以是 38:23.931），
  `Wed Oct 14 19:38:40 CST 2026 WARN` 那种完整时间是 MySQL 驱动自己用 jul 打的，不走 Spring 的 pattern。
- 排查心得（讲给用户）：日志里真正要看的是业务 DEBUG 的 SQL 行，驱动 WARN 可以整体过滤掉。

## 新 bug：seckillVoucher 第 249 行 NPE（serviceById 为 null）

- 堆栈：`java.lang.NullPointerException at VoucherOrderServiceImpl.seckillVoucher(VoucherOrderServiceImpl.java:249)`，
  第 249 行 = `if (LocalDateTime.now().isBefore(serviceById.getBeginTime()))` → `serviceById` 为 null，
  即 `seckillVoucherService.getById(voucherId)` 没查到行、返回 null，然后对着 null 调 `getBeginTime()`。
- 线程名 `[o-8081-exec-290]` 说明是压测/高并发场景，多半是批量请求里用了 tb_seckill_voucher 里不存在的 voucherId。
- 关键 DB 事实（来自 db/hmdp.sql）：`tb_voucher` 只有 1 条种子数据 —— id=1，type=0（**普通券**，不是秒杀券）；
  `tb_seckill_voucher` **一条种子数据都没有**，全靠调"新增秒杀券"接口自己插。
  所以拿普通券 id（如 1）去请求秒杀接口，必然 getById 返回 null。用户自建的秒杀券是 voucher_id=52。
- 修复方向：246 行拿到结果后先判空，`serviceById == null` 就 `return Result.fail("优惠券不存在")`，别让它抛到 WebExceptionAdvice。
- 这是 10-13 那次 review 提醒过的坑（当时说"246 行没判空，券不存在时 NPE"），这回真踩了 → 要在后续 review 持续盯"查库结果直接用"。
- 另注：MvcConfig 的 LoginInterceptor 排除的是 `/voucher/**`，**不匹配** `/voucher-order/**`，所以秒杀接口需要登录，
  带了 token 时第 268 行 `UserHolder.getUser()` 正常；压测不带 token 会被拦截器拦在 401。
