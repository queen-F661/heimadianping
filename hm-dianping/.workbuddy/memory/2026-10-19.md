## 黑马点评：逻辑过期方案 queryByIDBreakdown02 空指针排查

- 现象：ShopServiceImpl.java:186 `expireTime.isAfter(now)` 抛 NPE，压测多线程连续报错。
- 根因：Redis 里 `cache:shop:1/2` 存的是**裸 Shop JSON**（之前跑 queryByIDPenetration / queryByIDBreakdown01 写入，带 30 分钟 TTL），
  而 Breakdown02 期望 `RedisData{expireTime, data}` 包裹结构 → 反序列化后 expireTime=null → NPE。
- 处理：已直连 192.168.45.128:6379 删除两个脏 key（cache:shop:1、cache:shop:2），未改代码（用户习惯自己动手）。
- 待修的两个必踩坑：
  1. 180 行 `Shop shop = (Shop) date.getData();` —— RedisData.data 是 Object，Hutool 反序列出 JSONObject，强转必 ClassCastException。
     正解：`JSONObject o = (JSONObject) redisData.getData(); Shop shop = BeanUtil.toBean(o, Shop.class);`
  2. 202 行 DB 查不到时写 `""` 空值 → 下次读出又被当 RedisData 解析 → NPE 死循环。174 行需同时过滤空串。
- 其它提醒：unlock() 的 get+del 非原子，应复用已有的 UNLOCK_SCRIPT（Lua）；逻辑过期方案缺 saveShop2Redis 预热方法，
  未预热的 key 首次访问会直接 return null。
- 结论：切换缓存方案（穿透/互斥锁/逻辑过期）时，三套方案写入的 value 结构互不兼容，必须清 Redis 或换 key 前缀。

## Hutool 5.7.17 实测结论（探针验证）

- `JSONUtil.toJsonStr(RedisData)` 把 LocalDateTime 序列化成**毫秒时间戳**（如 1792415368227），
  但 `toBean` 能正确还原成 LocalDateTime，可以放心用。
- `RedisData.data` 是 Object，反序列化出来确实是 `cn.hutool.json.JSONObject`，强转 Shop 必 ClassCastException。
- 旧格式（裸 Shop JSON）被 toBean 成 RedisData 时，expireTime 和 data 都是 null —— 完整复现 NPE。
