## 秒杀压测 100% 异常排查（Redisson 锁）

用户用 JMeter 200 并发压 `/voucher-order/seckill/52`，聚合报告异常 100%、平均 304ms。

**结论：不是 Redisson 故障，是业务全部走了 fail 分支，HTTP 状态码全是 200。**

证据链：
- 日志里没有任何 ERROR 堆栈（WebExceptionAdvice 会 log.error），说明没抛异常
- `VoucherOrderMapper.selectCount` 出现 3 次，全部 `<== Total: 1`，说明用户 1010 早已下过单
- selectById 上百次但 selectCount 只有 3 次 → 其余请求全死在 `tryLock()` 返回 false
- 锁是正常释放的（否则后续不会再有请求进 selectCount）

代码侧问题（VoucherOrderServiceImpl）：
1. `Lock.tryLock()` 无参 = 不等待，抢不到立即 false，200 并发同用户只有 1 个能进
2. 压测姿势错：同一个 token/userId 重复秒杀，一人一单拦截必然生效，应该用多用户 token 压
3. 每请求 `getById` 打库，券信息没缓存；HikariCP 默认 10 连接，304ms 主要是排队
4. `createVoucherOrder(Long)` 里 `new RedisIdWorker(stringRedisTemplate)`，类已是 @Component，重复 new
5. Stream 异步版 `createVoucherOrder(VoucherOrder)` 没有 @Transactional，内部类里也拿不到代理
6. 变量名 `Lock Lock` 首字母大写，不符合 Java 规范

架构现状：seckillVoucher 仍走同步链路（查库→锁→查订单→扣库存→insert），Lua+Stream 那套优化代码写了但还没接上。

## 当日补充

用户用 JMeter「查看结果树」确认响应体为 `{"success":false,"errorMsg":"乱码"}`，坐实了"HTTP 200 + 业务失败"的判断，不是 500 也不是 401。
乱码原因：JMeter 默认按 ISO-8859-1 解析响应，需在 `bin/jmeter.properties` 里设 `sampleresult.default.encoding=UTF-8` 并重启。

## 库存98/订单1条 追查（关键结论）

现象：压测后 stock=98（扣2次），但 tb_voucher_order 只有 1 条。

取证（连 MySQL + Redis 实测）：
- `icr:order:2026-10-23 = 2`，订单 id=923245671731953666 低 32 位 increment=2
- `nextId()` 只在扣库存成功后才调用 ⇒ 今天恰好成功 2 单
- `lock:order:1010` 不存在，锁已正常释放，无残留
- `SHOW INDEX FROM tb_voucher_order` 只有 PRIMARY，**没有 (user_id, voucher_id) 唯一索引**

结论：**原子性没失效**。差的那 1 条是用户手动 DELETE 删掉的，而 DELETE 订单不会归还库存 ⇒ 库存永久少 1。
已给出干净验证方案：清订单+重置 stock=100 → 记录计数器 N0 → 跑一轮压测 → 比对 stock/订单数/计数器增量。
建议必做兜底：`ALTER TABLE tb_voucher_order ADD UNIQUE KEY uk_user_voucher (user_id, voucher_id);`

## 踩过的判断偏差（教训）

MyBatis 日志 `<== Total: N` 是**返回结果行数**，不是查询的值。`COUNT(*)` 永远返回 1 行，所以 selectCount 的 `Total: 1` 与 count 实际值无关。第一轮分析曾误读，需避免。
