## 秒杀 Lua 脚本报错排查（seckill.lua:15）

**报错**：`RedisSystemException ... @user_script:15: attempt to compare nil with number`
调用链：VoucherOrderController.seckillVoucher → VoucherOrderServiceImpl.seckillVoucher:248（stringRedisTemplate.execute 执行 seckill.lua）

**根因（双层）**
1. 直接原因：`tonumber(redis.call("get", stockkey)) < 0`。key 不存在时 redis.call get 返回 Lua 的 false，`tonumber(false)` = nil，`nil < 0` 直接抛错中断脚本。
2. 真正原因：Redis 里没有对应的库存 key。实测（直连 192.168.45.128:6379）只有 `seckill:stock:103`=100，`seckill:order:*` 为空。全项目仅 `VoucherServiceImpl.addSeckillVoucher()` 会写 `seckill:stock:`，数据库里已有/手动插入的券不会自动预热。

**附带发现的逻辑 bug**
- `< 0` 应为 `<= 0`：库存为 0 时也会 incrby -1，导致超卖成负数。
- `seckill.lua` 末尾没有 XADD 到 `stream.orders`，但 Java 侧 VoucherOrderHandler 已在消费 Stream —— 抢券成功也不会生成订单。
- `VoucherOrderServiceImpl` 第 130、164 行 `acknowledge("s1", "g1", id)` 第一个参数写成了 "s1"，应为 "stream.orders"，否则消息永远留在 pending-list。
- Lua 里 key 全用字符串拼接、Java 传 `Collections.emptyList()` 作 KEYS，单机没问题，集群模式会 CROSSSLOT。

**结论/约定**：库存 key 必须在抢券前预热（新增券接口 or 手动 SET），Lua 必须做 nil 兜底后再比较。

## 第二轮改造：统一成阻塞队列版（用户要求）

用户中途自行把 Handler 改回 `orderTasks.take()`，导致 **Stream 与内存队列两套并存**，且写入 4 个 bug。

### 代码改动
1. `seckill.lua`：删掉 `xadd` 与 `ARGV[3]`，回到两参数；保留 nil 兜底与 `<= 0`。
2. `VoucherOrderServiceImpl`：
   - `init()` 删除 `initStreamGroup()` 调用，并整体删除该方法（Stream 方案下线）。
   - `VoucherOrderHandler`：`while(running)` + `orderTasks.take()`，InterruptedException 时按 `running` 决定退出，外层 catch 兜底单个订单异常。
   - `seckillVoucher()`：**只生成一个 orderId**（原来生成两次导致前端拿到的号与入库号不一致）；执行 Lua（两参数）→ 组装 VoucherOrder → `proxy = AopContext.currentProxy()` → `orderTasks.add()` → `Result.ok(orderId)`。
   - `createVoucherOrder()`：`UserHolder.getUser().getId()` → `voucherOrder.getUserId()`（后台线程无 ThreadLocal，原写法必 NPE）；两处 `.eq("voucher_id", voucherOrder)` → `voucherOrder.getVoucherId()`。
   - `destroy()`：`shutdown()` → `shutdownNow()`（打断阻塞中的 take()）。
   - 删掉第 134 行孤立的 `;`。

### 编译验证
- 本机仅 JDK21 时 maven 报 lombok `NoSuchFieldError: JCImport.qualid`（lombok 1.18.22 与 JDK21 不兼容，非代码问题）。
- 改用 `C:/Users/zhy/.jdks/dragonwell-1.8.0_502` 编译通过，`target/classes/seckill.lua` 与 class 均已更新。
- 编译命令：`JAVA_HOME=~/.jdks/dragonwell-1.8.0_502`，maven 用 IDEA 自带 `plugins/maven/lib/maven3/bin/mvn`。

### 教学要点（已讲）
- 一人一单本质 = `SISMEMBER seckill:order:{voucherId} {userId}`，一个 Set 就是一张按券号开的签到表。
- 三道防线：Lua(快) → Redisson 锁(串行) → DB count(最终账本)。
- `AopContext.currentProxy()` 是 ThreadLocal，必须在请求线程取并缓存到字段，后台线程取会抛 IllegalStateException。
- 阻塞队列版短板：纯内存，服务重启未落库的订单全丢；Stream 版才有 ack + pending-list 兜底。

## 第三轮：审用户的 draw.io 流程图（一人一单）

用户自己用 draw.io 画了 48 个节点的 mxGraphModel 流程梳理图，暴露出 5 处理解偏差：

1. 顺序反了：把「放队列 → 定义队列/线程池 → 开线程」画成串行。实际三者不在同一时间点：字段在类加载时建、线程在 `@PostConstruct` 启动、add 在请求时发生。
2. 把「判断 Lua 返回值是否为 0」画了两次，第二次错放在 `createVoucherOrder` 内部（进到该方法时早已确定是 0，那里的判断是 DB count 查重）。
3. 误以为 `createVoucherOrder` 里要从阻塞队列再取 userId/voucherId；实际只在 `take()` 取一次，之后从 `VoucherOrder` 对象 get。
4. 写成「数据库的添加和删除」，实际只有 insert。
5. 把两条并行的时间线（请求线程 / 后台线程）画成了一条串行线，导致越看越乱。

**纠正方式**：给他画了「按时间顺序 + 左侧标注执行者（请求线程 / Redis / 后台线程）+ 中间画线程交接虚线」的主干图。

**用户习惯**：喜欢边学边用 draw.io 画流程图复述逻辑，后续可主动提供 mermaid/draw.io 源码而非只给文字。
